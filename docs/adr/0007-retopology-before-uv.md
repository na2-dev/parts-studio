# UV展開の前にリトポロジー（面の並べ直し）を入れる

ADR-0002 で「UV展開を独立工程にし、xatlas で自前に行う」と決めた。**展開器の選択が問題の本質
ではなかった**ことが実測で分かったので、決定を訂正して補う。

書き出した glb の UV を測ったところ、**9,977 チャート・チャートあたりの面数の中央値が 1 面**
という状態だった（[実測](../measurements/2026-08-30-uv-unwrapping.md)）。まともな展開なら
数十〜数百チャートに収まる規模である。

原因を切り分けた結果:

- `to_glb` のチャート分割の設定（`refine_iterations` / `global_iterations`）を上げても**改善しない**
  （10,496 → 11,196 とむしろ微増）
- 面数を 30 万 → 6 万 → 2 万と減らすとチャート数は減るが、2 万面でも 1,150 チャート・中央値 3 面
- **xatlas に差し替えると、むしろ悪化する**（6 万面で cumesh 2,777 に対し xatlas 4,142、
  利用率も 58.8% → 50.1%）

つまり**展開器ではなく、入力メッシュの面の並びが原因**である。マーチングキューブ／
デュアルコンタリングが吐くのは大きさも向きも不揃いな三角形の寄せ集めで、どの展開器にかけても
砕ける。Tripo も公開資料で同じことを述べている（「散らかった形状を展開すると UV 島が断片化する。
だからリトポロジーが UV に先行する」）。

**したがって、UV 展開の前に面を四角い網目へ並べ直す工程を入れる。** 展開器は当面 `to_glb` 内蔵の
`cumesh.uv_unwrap` のままでよい（xatlas より良い数字が出ている）。並べ直したあとで両者を測り直し、
そこで初めて選ぶ。

3d-studio が同じ壁に 2026-08-16 に当たっており、Blender による並べ直し（`tools/remesh_blender.py`）
と、低ポリ化＋法線マップ焼き戻し（`tools/retopo_bake_blender.py`）を持っている。**移植する。**
そこに記録されている順番の制約も引き継ぐ。

- 並べ直しは**色塗りのあと**（前にやると効かない。実測で 59,999 → 59,999 と無反応）
- 並べ直しは**骨入れの前**（スキンウェイトは頂点ごとに付くため、後にやると壊れる）

## Consequences

Blender（`bpy`）への依存が増える。`bpy` は GPL なので、別プロセスとして起動する形にする
（3d-studio も同じ運用）。配布形態を決めるときに再検討する。

## Considered Options

- **xatlas に差し替える（ADR-0002 の当初案）**: 実測で cumesh より悪かった。単独では採らない。
  並べ直し後に測り直して判断する。
- **チャート分割の設定を詰める**: 効かないことを実測した。却下。
- **面数を減らすだけ**: 効果はあるが不十分（2 万面でも 1,150 チャート）。並べ直しと併せて使う。
