# 作業の進め方

## ブランチと PR

- **必ず `main` から新しいブランチを切る。** ブランチ間で PR がコンフリクトしないようにするため
- **タスク 1 つにつき PR 1 つ。** タスクは [docs/tasks/README.md](tasks/README.md) で管理する
- PR のタイトルは**何をしたかが一行で分かる**ものにする
- PR の本文は**視覚的に**まとめる。文章を並べるのではなく、表・画像・図で。
  人がレビューしやすいことを優先する

## PR を出す前に必ず通すもの

| 変更したもの | 実行するもの |
|---|---|
| ドキュメント | `/doc-review` |
| コード | `/code-review` |

指摘は**PR を出す前に直す**。直さない場合は、なぜ直さないかを PR 本文に書く。

## 実装が伴うタスク

- テストを書く。テストが書けない性質のもの（生成物の見た目など）は、
  **判定の手順と基準**をドキュメントに書く
- 見た目の変更は**画像を並べて確認する**。数字だけで良し悪しを判断しない
  （シルエット IoU が 0.9 台でも実物が塊だったことがある。3d-studio の記録より）

## ドキュメントを直すとき

- **`docs/measurements/` は書き換えない。** 当時の記録なので、
  変わったことは**注記を足す**だけにする
- **ADR は書き換えず、冒頭に訂正注記を足す。** 決定を覆したときは、
  **覆された側の ADR にも注記を足す**（覆した側だけに書くと、
  一覧から古い ADR を開いた人が古い決定を正だと思う）
- **用語（CONTEXT.md）を直したら、その用語を使っている他の項も見る。**
  1 つの項だけ直すと、その項に依存している別の項が宙に浮く
- 文言を変えたら、**変更前の文言そのもので grep** して全部の出現箇所を洗う

## 測るときの約束

- **GPU を空けてから 1 つずつ走らせる。** 同時に走らせると所要時間の測定が壊れる
  （実測で 2048 の見積もりを 4 倍に見誤った）
- 数字は必ず**どの機体・どの設定で測ったか**を添える
