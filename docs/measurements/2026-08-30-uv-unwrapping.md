# 書き出した glb の UV を測る（2026-08-30）

今日の品質判定はすべて**ボクセル場を直接サンプリングした描画**で行っていた
（`PbrMeshRenderer` は `MeshWithVoxel` を受け取ると `grid_sample_3d` で 3 次元の属性場を直接引く。
`pbr_mesh_renderer.py:324-333`）。**実際に出力される glb を一度も見ていなかった**ので測った。

## 最初の測定（既定の設定）

```
面 289,493 / 頂点 215,738 / アトラス 2048x2048
UVチャート数            9,977
チャートあたりの面数     中央値 1面
上位10チャートの占有率   7.8%
アトラス利用率          56.0%
```

**中央値が 1 面**。メッシュの大半が三角形 1 枚ずつ独立した島に分解されている。

## 切り分け1: チャート分割の設定は効かない

`to_glb` は `cumesh.uv_unwrap` の円錐クラスタリングを使い、既定が
`refine_iterations=0` / `global_iterations=1` と最小設定だった。上げれば改善すると考えたが、外れた。

| | 面数 | チャート数 | 中央値 | 最大 | 利用率 |
|---|---|---|---|---|---|
| A: 30万面・refine 0 / global 1（既定） | 288,545 | 10,496 | 1 | 2,620 | 55.6% |
| B: 30万面・refine 4 / global 4 | 289,499 | **11,196** | 1 | 2,635 | 58.1% |
| C: 6万面・refine 4 / global 4 | 56,797 | 2,777 | 2 | 670 | 58.8% |
| D: 2万面・refine 8 / global 8 | 18,768 | 1,150 | 3 | 268 | 59.9% |

**設定を上げるとむしろ微増した。効いたのは面数だけ。** ただし 2 万面まで削っても
1,150 チャート・中央値 3 面で、まともな展開（数十〜数百チャート）には遠い。

## 切り分け2: xatlas に替えると悪化する

ADR-0002 の当初案どおり xatlas（0.0.11・MIT）で同じ形を展開し直した。

| | cumesh | xatlas |
|---|---|---|
| 6 万面 | 2,777 チャート / 58.8% | **4,142 / 50.1%** |
| 2 万面 | 1,150 チャート / 59.9% | **1,633 / 52.3%** |

**xatlas のほうが悪い。** 展開器の問題ではない。

## 結論: 入力メッシュの面の並びが原因

マーチングキューブ／デュアルコンタリングが吐くのは、大きさも向きも不揃いな三角形の寄せ集め。
どの展開器にかけても砕ける。Tripo の公開資料も同じことを述べている
（「散らかった形状を展開すると UV 島が断片化する。だからリトポロジーが UV に先行する」）。

3d-studio は 2026-08-16 に同じ壁に当たっており、`tools/remesh_blender.py` の冒頭にこう書いてある。

```
Tripoのモデル … 18,368面できれい
うちの出力    … 60,000面あるのにガタガタ
AIが作った形は「等高線から削り出した」ような面の並びなので、面数を増やしても
なめらかになりません。並べ直すと【少ない面で、よりきれい】になります。
おまけに、面が少ないほど1面あたりに使える色の絵が広くなるので、色塗りも細かくなります。
```

→ [ADR-0007](../adr/0007-retopology-before-uv.md)

## まだ確かめていないこと

**この断片化が見た目にどれだけ響くかは未検証。** glb を同じカメラで描画しようとしたが、
`MeshWithPbrMaterial` の作り方が足りずネイティブ側で落ちた。数値上は悪いが、
焼き込み自体はテクセル単位でボクセル場から引いているので、色そのものは正しく載っている可能性がある。
**影響が出るのは、継ぎ目のフィルタリングと、テクスチャ画像を書き換える後処理**
（`project_detail.py` のような方式）のほう。
